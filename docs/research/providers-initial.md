# Provider feasibility research

Checked 2026-11-13. Research only: no installs, sign-ins, inference calls, credential reads, app edits, or publishing. Official public documentation was searched and fetched. No account-specific access or end-to-end behavior has been verified.

## Decision summary

- **ChatGPT plan usage: officially documented candidate.** A locally hosted/open-source desktop client can use its own Sign in with ChatGPT authorization and eligible plan usage through the public Responses API. Identity sign-in and inference permission are separate. Paid/remotely hosted distribution needs the separate partner/interest route. Availability remains conditional on the selected account, workspace, region, model, consent, and integration.
- **Muse Code: keep pending/disabled.** An official Rust SDK and host-owned authentication exist, but the current published tool restriction contract does not establish enforceable chat-only operation. The host is also not on PATH here. Do not replace this with a direct API request carrying a Muse subscription credential.
- **BYOK: documented adapters, not tested connections.** Claude, Gemini, Grok, and OpenRouter expose official API paths. A generic compatible server is a user-selected endpoint with unverified capabilities until checked. An API key means that API account's billing, not a consumer chat subscription.

## ChatGPT: supported authorization, with explicit plan consent

The official open-source guide covers open-source and locally hosted apps. The consent grants optional plan usage for eligible Responses requests; it grants neither access to ChatGPT conversation history nor account context. The guide directs paid or remotely hosted apps to an interest form. The quickstart identifies eligible Plus and Pro users, so do not imply every account or subscription qualifies. [Overview](https://developers.openai.com/siwc/token-sharing-open-source), [Quickstart](https://developers.openai.com/siwc/quickstart)

Use a new application-owned OAuth flow in the system browser, with loopback callback, fresh state/nonce, PKCE, a persisted `ext_agent_host_id`, and the issued client registration. Retain the returned client ID before code exchange. Verify identity and returned scopes. The documented scope set includes identity scopes, `offline_access`, `resource.invoke`, and `chatgpt.tokens.use.direct`, using resource `https://api.openai.com/v1`. Only the granted direct-use scope enables plan inference. Store the new app's credentials securely; do not import Codex/ChatGPT credential files or replay existing sessions. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [Official desktop integration example](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)

With this OAuth access token, use `GET https://api.openai.com/v1/models`. This route returns a `models` array: display `display_name`, select rows with `visibility == "list"`, and send the selected `slug`. Preserve ordering and refresh on account changes. Inference uses `POST https://api.openai.com/v1/responses`, bearer OAuth, `store:false`, `stream:true`. Never use a ChatGPT `backend-api` endpoint. A stream is successful only after `response.completed`; partial output alone is not success. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)

For HTTP history, send the necessary history as an `input` array and omit `previous_response_id`. Use `instructions`/developer messages rather than explicit system message items. Several ordinary Responses fields are unsupported, including `max_output_tokens`, `temperature`, `top_p`, `metadata`, `background`, and `conversation`. Web search depends on model and account/workspace policy. Hosted image generation, file search, Code Interpreter, computer use, MCP/connectors and `tool_search` are unsupported on this route; text/images/files depend on the selected model, while audio/video and Files uploads are unsupported. Use the exact preview contract, not the unrestricted API-key contract. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

Declined plan consent leaves identity connected but inference disabled. Usage-limit, eligibility, policy, or admission errors must stop that route. Keep the actual HTTP status, provider error, and request ID; do not silently retry with an API key. Offer an explicit connection/billing choice. A `429` plan-limit error does not prove the user's whole plan is empty or reveal its reset time. [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)

Truthful copy:

- Before authorization: **Continue with ChatGPT** — “Connect your ChatGPT account. Eligible plans can be used after you allow plan usage.”
- Identity-only result: **Signed in · Plan usage not enabled** — “Allow ChatGPT plan usage to send messages with this connection.”
- Only after verified scope and route: **ChatGPT plan usage enabled**; **Manage usage**.
- Preview/mock: **Preview connection** — “Sign-in and live requests are not connected in this preview.”
- Limit/error: “ChatGPT plan usage is unavailable for this request. Choose a different connection to continue.” Never auto-switch.

## Muse Code: SDK is real; strict tool removal is the blocker

The official SDK site is linked from Meta's Muse Code documentation. Its `latest/` redirect resolves to the `1.4/` documentation. The official crate is **`muse-code-sdk`**, not the similarly named third-party `muse-codes`. Public crates.io metadata reported version **1.4.14** and repository `meta-models/muse-code-sdk` at research time. The Rust SDK is asynchronous, uses the caller's Tokio runtime, requires Rust 1.97+, and does not bundle the `muse` host. Pin the crate exactly to the installed host's `X.Y.Z`; fingerprint mismatch is a warning and can leave incompatible calls possible. [Meta integration entry](https://dev.meta.ai/docs/muse-code), [Rust SDK, current release](https://meta-models.github.io/muse-code-sdk/1.4/reference/rust/), [Official crate](https://crates.io/crates/muse-code-sdk)

The client spawns local `muse serve` and communicates over MSP/stdin-stdout. This is a local agent host, not local model inference: Muse calls the Meta model service. Ordinary host approval callbacks and read-only profiles do not mean “no tools”: safe actions can run automatically, and read-only still permits reading. The `untrusted` approval mode does not gate every file tool. [Sessions and turns](https://meta-models.github.io/muse-code-sdk/next/guides/msp-concepts/sessions-and-turns/), [Authentication](https://dev.meta.ai/docs/muse-code/auth), [Permissions and safety](https://dev.meta.ai/docs/muse-code/permissions)

The **release 1.4 `SessionConfig` has no `allowedBuiltInTools` field** and says unknown keys are ignored. The **`next` developer-preview schema** describes `allowedBuiltInTools: []` as no built-in tools, but also says the host refuses every specified value until enforcement lands. Therefore adding this field is not proof of safety: released hosts may ignore it, while newer preview hosts may refuse it. A system prompt, deny-all approval callback, empty workspace, or read-only sandbox cannot substitute for confirmed removal of shell/filesystem/coding tools. Keep Muse disabled until an official shipped host proves effective exclusion, including inherited MCP/plugins/hooks and indirect execution paths. [Released SessionConfig](https://meta-models.github.io/muse-code-sdk/1.4/generated/msp/types/sessionconfig/), [Preview SessionConfig](https://meta-models.github.io/muse-code-sdk/next/generated/msp/types/sessionconfig/)

Host-owned `account/loginStart` supports device-code login and returns the verification URL/user code; this account surface is experimental. `account/read` reports the effective credential lane without returning secrets. The documented lane values include `accountLogin`, `apiKey`, `envKey`, and `loggedOut`. `usage/read` returns last-observed subscription usage, possibly absent, with a timestamp; do not display stale observations as live balances. `accountLogin` by itself does not establish an active subscription. [Host login](https://meta-models.github.io/muse-code-sdk/1.4/generated/msp/methods/account-loginstart/), [Account state](https://meta-models.github.io/muse-code-sdk/1.4/generated/msp/types/accountstatekind/), [Usage read](https://meta-models.github.io/muse-code-sdk/next/generated/msp/methods/usage-read/)

Muse subscriptions apply to the credential connected during CLI onboarding, for use with Muse Code only. Additional API keys are pay-as-you-go. `META_API_KEY` takes priority, then a stored API key, then browser login. This means starting a host does not by itself select plan billing. Block the plan connection if the effective lane is API-key based or unknown. The public subscription page expressly says the subscription works through the signed-in Muse Code CLI; SDK host use is plausible because it drives that host, but a generic chat app entitlement is **not separately established** by these pages. Do not claim verified plan billing. Contributor mode also changes data use and defaults can differ; do not claim privacy behavior without reading host-reported state. [Subscriptions](https://dev.meta.ai/docs/muse-code/subscriptions), [Credential precedence](https://dev.meta.ai/docs/muse-code/auth)

Truthful copy:

- **Muse · Pending verification** — “The official Muse host integration is not ready for chat-only use.”
- Host missing: **Muse host not found** — “Muse Code must be installed and verified before this connection can be enabled.”
- Billing uncertain: **Plan usage not verified** — “This host has not confirmed a subscription route.”
- Future verified host description: “Muse runs a local connection process and sends model requests to Meta.” Avoid “runs locally” alone.

## BYOK adapters and discovery

|---|---|---|
| Claude | `https://api.anthropic.com/v1/messages`; `GET /v1/models`. Current docs prefer `Authorization: Bearer` and still support `x-api-key`; include `anthropic-version` and workspace selection where the key requires it. | Native Messages with content blocks and SSE. Anthropic server web search returns cited sources; use the documented supported version and limits. | Gemini | Recommended native route is `POST https://generativelanguage.googleapis.com/v1beta/interactions`, `x-goog-api-key`, documented `Api-Revision`. SSE example uses `?alt=sse` plus `stream:true`. `GET /v1beta/models` supplies metadata. | Interactions uses `input` and typed `steps`; `store:false` supports client-owned history. Tool `google_search` supplies search steps and URL citations. `generateContent` remains supported but is legacy for new work. [Get started](https://aistudio.google.com/docs/get-started), [Interactions overview](https://ai.google.dev/gemini-api/docs/interactions-overview), [Models](https://aistudio.google.com/api-reference/models) |
| Grok | `POST https://api.x.ai/v1/responses`, bearer API key; `GET /v1/models` or richer `/v1/language-models`. | Responses-style streaming; official `web_search` tool, with X Search separately. Do not assume every model or region supports every tool. [Quickstart](https://docs.x.ai/developers/quickstart), [Models](https://docs.x.ai/developers/rest-api-reference/inference/models), [Web search](https://docs.x.ai/developers/tools/web-search) |
| OpenRouter | `POST https://openrouter.ai/api/v1/chat/completions`, bearer API key; `GET /api/v1/models`. Also supports Responses/Messages routes. | Chat Completions is a straightforward adapter. Server tool `openrouter:web_search` requires tool support; older web plugin behaves differently. Discover `supported_parameters` and endpoint capabilities. [Chat API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request), [Models](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties), [Server tools](https://openrouter.ai/docs/guides/features/server-tools) |
| Custom compatible | User-specified base URL, explicitly selected protocol, optional API key, and model ID or server model discovery. | “Compatible” does not guarantee Responses, model listing, search, vision, tools, or SSE parity. Default advanced capabilities to unknown/disabled and enable only after a documented adapter or successful capability verification. This is an implementation recommendation, not a universal provider contract. |

OpenRouter defaults to provider failover within a model. This is distinct from switching the app to another billing connection, but can still change the serving provider. For strict route choice, omit model-fallback arrays and configure `provider.allow_fallbacks:false` plus the intended provider restriction; surface the chosen route. Never silently move from ChatGPT/Muse plan usage to a BYOK account. [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)

Common BYOK copy: **Use API key** — “Requests use this provider's API billing.” Keep **Key saved**, **Connection verified**, and **Live request completed** as different states. Model names in an unauthenticated preview are examples, not available account models. Search toggles must reflect the selected adapter/model/account, with citations rendered from provider metadata rather than invented URLs.

## Local inspection evidence and limits

No relevant local documentation was surfaced by the bounded package/app checks, so official web documentation supplied the OpenAI contract. `muse`, `muse-code`, `musecode`, `rustc`, and `cargo` were not on PATH. No credential files, environment values, keychain entries, or stored account sessions were read.

Before any eventual live implementation is labeled ready: verify the actual shipped host/protocol, selected account permission and billing route, model discovery, stream completion/cancellation/error handling, and effective absence of forbidden tools. At this research stage, none of those live checks have occurred.
