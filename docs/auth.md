# Credentials and ChatGPT sign-in

Implemented against the official OpenAI documentation checked on 2026-11-13 using the OpenAI Docs skill. The local tests use synthetic values and signing keys generated only in memory. No live account authorization or plan inference has been attempted.

## Credential boundary

`credentials::KeychainStore` uses the macOS generic-password service `app.melly.desktop.credentials`. There is no file, SQLite, environment, browser-storage, or other-application credential fallback. `MemorySecrets` is the public in-memory test double and redacts its debug representation. Authentication records do not implement `Debug`.

Provider keys are entered through `src-tauri/src/secure_input.rs`: AppKit `NSAlert` with `NSSecureTextField`, dispatched through `AppHandle::run_on_main_thread`. Only Rust receives the value. The command caller writes it to the vault and returns success/cancel to the frontend. Empty input is treated as cancel; error messages omit input values.

Melly never requests the Mac login password. Secret reads, writes, updates and deletes explicitly use Security.framework's `kSecUseAuthenticationUIFail` policy. The legacy login Keychain can ignore that per-query option for item ACLs, as a native sign-in check exposed. Every operation also takes a serialized, scoped `SecKeychain::disable_user_interaction` guard; its prior interaction setting is restored on success, error or unwind. Protected or inaccessible items fail closed. Presence checks request attributes only and skip authentication-requiring items. A vault failure cannot prevent history, settings or Demo from opening. There is no interactive retry or plaintext fallback. [Apple per-query policy](https://developer.apple.com/documentation/security/ksecuseauthenticationuifail), [legacy Keychain interaction policy](https://developer.apple.com/documentation/security/seckeychainsetuserinteractionallowed(_:))

## App-owned authorization

Melly persists a fresh host UUID in its pending Keychain namespace and opens the system browser through a Rust callback. First authorization uses `client_id=dynamic_agent_client` and `agent_name_hint=Melly` at `https://auth.openai.com/api/accounts/authorize`. The validated loopback callback supplies the issued `oaiapp_…` registration, which is saved before code exchange. Retries in that namespace reuse its host and registration. This is the documented dynamic-registration entrypoint; it is not a separate registration API. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)

Every attempt binds an available IPv4 loopback port at `/auth/callback` before opening the browser, creates fresh random state/nonce/PKCE material, and uses the exact callback URI for authorization and exchange. Callback state, host, port, path, expiry, duplicates, and returning client identity are checked. Browser replies contain only generic text. The attempt expires after five minutes and supports cancellation.

The native browser handoff validates the exact official authorization origin/path, cancels the listener if browser launch fails, and permits an immediate retry. Both initial and terminal connection events are published under a generation check held through delivery, so a disconnected or older attempt cannot overwrite a newer attempt's status.

The requested scopes are `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, with resource `https://api.openai.com/v1`. Identity and inference permission remain separate. Identity-only completion is retained, produces a visible plan-permission error, and cannot supply an inference token. An explicit retry after identity-only consent requests `prompt=consent`; ordinary reauthorization does not force consent. [Consent recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)

Tokens are exchanged only at `https://auth.openai.com/api/accounts/oauth/token`. OpenID discovery and JWKS URLs are pinned to the documented OpenAI values. The JWT verifier checks an allowed asymmetric signature and key usage, issuer, client audience, expiration, issued-at, nonce, and returning subject. Unsupported metadata, HTTP redirects, oversized responses, and invalid identities fail closed. Network/error messages retain safe status/code/request-ID details and omit request and response bodies. [Identity verification and discovery](https://developers.openai.com/siwc/website)

## Credential namespaces and development rebuilds

The desktop stores each ChatGPT authorization under immutable Keychain account names `chatgpt.ns.<UUID>/<record>`. A namespace contains only Melly's host, registration, session, generation and saved-plan marker records. API keys continue to use the base vault. `AuthNamespaces` accepts only those five auth record names and never falls back to legacy, unprefixed records.

An explicit Continue with ChatGPT creates a pending namespace separate from the active connection. Retries reuse that pending namespace within the current process. After a restart or rebuild, the next explicit attempt starts a fresh namespace without reading the old pending, active or legacy secret records. This allows new authorization when an earlier development binary's Keychain item access rules deny the rebuilt binary. Existing protected records are neither imported nor modified, and their access rules are not weakened.

The app-data file `chatgpt-namespaces.json` contains only `active` and `pending` UUID selectors (or null). It holds no host ID, client ID, identity or credential. Reads are bounded; writes use a private mode-0600 temporary file and atomic replacement. A pending namespace becomes active only after verified identity and plan consent, while the native LoginState generation guard is held. Failure, cancellation or failed persistence preserves the previous active selection. A restart uses the saved active selector; an absent selector selects an empty, disconnected vault without probing legacy secrets.

Malformed or unreadable selector metadata leaves ChatGPT disconnected with a visible recovery status; healthy history, Demo and other providers still open. Startup leaves the original file untouched. Explicit sign-in or disconnect preserves a damaged regular file under a fresh `chatgpt-selection-preserved-<UUID>.json` name with mode 0600 before saving new selectors. Its contents are never logged. A substituted link, directory or failed backup remains untouched and produces a recovery error; no unsafe path is followed to force recovery.

Every sign-in, token read and renewal captures an immutable scoped vault. Changing the selection cannot redirect an in-flight refresh into another namespace. A renewal already sent to the service may finish saving a rotated token in its detached namespace, but cannot select it again. The engine rejects a credential result if the selected vault changed while that credential was being obtained.

## Renewal and connection status

The token record holds the verified identity, issued client ID, granted scopes, tokens, and expiry together in Keychain. Refresh is serialized within the desktop process and replaces the entire token record in one vault write. Once requested, bounded credential renewal finishes independently of a chat cancellation, so stopping a reply cannot discard a rotated replacement. The application must run one instance to avoid competing refresh tokens across processes. Missing scope on refresh preserves the existing grant; an explicitly reduced grant disables inference. Terminal refresh errors clear tokens; temporary network/server errors retain them. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)

Orderly Quit closes admission to new auth work, cancels pending sign-in and queued renewals, and waits for credential operations independently of the active-chat count. A detached renewal is registered before spawning and remains counted through its final Keychain write. The drain has a 65-second limit, allowing the possible token, discovery and JWKS requests at their 20-second deadlines plus a margin. Idle auth work completes the drain immediately; repeated Quit cannot bypass it. Force Quit, process termination, system failure or expiry of the drain limit can still interrupt a rotated-token save and require fresh sign-in.

Startup uses `has_saved_plan`, a metadata-only presence check for the selected namespace's nonsecret `chatgpt.saved-plan.v1` marker. It never calls the credential-value getter or validates a token. The marker is written only after a verified plan grant is saved, and removed on identity-only consent, scope loss or terminal renewal failure. Its meaning is **saved plan connection, checked on use**; expiry and current entitlement are deliberately unknown at startup. Legacy records are not migrated by decrypting credentials during launch.

Bootstrap reports `Sign-in pending` while the native login token is active, so reopening the provider dialog can recover the in-progress state and cancellation action. Completion or cancellation clears that pending status; an existing active plan connection remains configured while a replacement is pending.

`is_connected` is a deeper helper that reads credentials and checks for an unexpired access token or an unexpired renewable session; it must not run during bootstrap. Neither status is live API verification. `access_token` renews near expiry, honors `earliest_refresh_at`, and is the only way the chat route receives an OAuth token. A successful refresh renews the documented 30-day refresh lifetime. Expired refresh credentials, absent scopes, mismatched registrations, and malformed records require sign-in. [Token lifetimes](https://developers.openai.com/siwc/token-sharing-open-source/token-reference)

The desktop supports one selected ChatGPT connection. Disconnect cancels pending login and removes the active/pending selectors without reading or deleting protected Keychain records. A metadata-write failure still detaches the current process and is reported; it cannot claim a persisted disconnect. The lower-level `auth::disconnect` helper remains available for a directly owned vault and clears its token/marker with a generation change, but the native namespace workflow does not call it. Remote revocation remains pending: users can remove Melly's access in [ChatGPT settings](https://chatgpt.com/settings/usage). Retained old namespaces, a multi-account picker and automated remote revocation are not managed by the current UI.

## Verification and pending checks

`cargo test -p melly-core auth --lib` covers authorization construction, callback/state guards, signed identity claims and key-use validation, exact consent scopes, token rotation/concurrency, temporary/terminal refresh errors, disconnect races, expiry status, marker lifecycle, real local loopback completion, HTTP error sanitization/redirect refusal, and cancellation. `cargo test -p melly-core --test auth` covers vault isolation/redaction, malformed/empty credentials, cancellation before browser launch, metadata-only startup status with a getter that panics, and disconnect preservation of unrelated keys and registration.

Eleven `auth_namespace` tests cover namespace isolation, UUID-only private persistence, process-only pending reuse, failure/cancellation preserving active selection, stale activation rejection, captured refresh isolation, persistence failure, unchanged API-key routing, browser handoff when old active/legacy records deny access, and safe recovery from malformed/unreadable metadata without losing healthy history. Auth shutdown regressions verify draining a rotated response after Stop, rejecting queued/new exchanges, bounded waiting, idle completion and cancelled sign-in tracking. The six native LoginState tests cover generation-guarded publication, pending status and browser handoff failure. These are synthetic tests; they do not authorize a real account.

The opt-in `native_keychain_roundtrip_without_authentication_ui` test passed on the Mac: a UUID-named synthetic credential was created, read, updated and deleted without authentication UI. Normal tests use an in-memory vault.

Pending live checks: eligible user/workspace consent, actual OpenAI discovery/JWKS and token exchange, model discovery, completed Responses inference on the plan route, and renewal/revocation with the real service. No live-ready claim follows from the offline tests. The provider adapter owns model/inference checks and must never switch to API-key billing after a plan-route error.
